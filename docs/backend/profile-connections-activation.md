`profile-connections.sql` is additive and deliberately fails on existing names. It adds four private RLS tables, participant/recipient policies, a NOLOGIN/NOINHERIT/NOSUPERUSER/NOBYPASSRLS function role, one narrowly scoped public-profile identity policy/column grant, and three authenticated RPC wrappers. No existing function, Auth policy, Storage policy or journey visibility rule is replaced. No direct relationship table grants or role membership are given to clients.

Ownership transfers temporarily grant the migration actor SET-role membership and grant `connection_rpc` CREATE on the private schema; both explicit temporary grants are revoked after the final transfer. Full proposal replay is tested as a controlled non-superuser CREATEROLE migration owner, not only as the fixture superuser. PostgreSQL 17 automatically gives a role creator a separate bootstrap-granted ADMIN-only membership (INHERIT=false, SET=false); this automatic role-administration record may remain, while no temporary SET/INHERIT capability or schema CREATE remains. It is distinct from application/client membership. Inspect actual `pg_auth_members` grantors/options after any approved activation; do not claim that all membership rows are absent.

RPCs return the exact camelCase contract in `src/lib/connections/types.ts`:

- `get_profile_connections(target_id uuid)` returns caller's own counts and relationship with target. Self-target is valid for own counts.
- `list_profile_connections(collection text, cursor text default null, page_limit integer default 20)` returns own friends/following/incoming/outgoing/inbox. Pages are capped at 50; cursors order by creation time + UUID. Counts/graph are never anonymous or another user's.
- `mutate_profile_connection(target_id uuid, action text, request_id uuid default null, expected_revision integer default null, enabled boolean default null, notification_ids uuid[] default null)` returns authoritative summary for that target. Actor comes only from `auth.uid()`.

Request IDs are per-intent UUIDs. One unordered pending pair is allowed; an opposite send reports incoming and never accepts. Recipient alone accepts/declines; sender alone cancels. Acceptance is atomic with friendship and sender notification. Request events remain after terminal transitions and join current status/revision. Removal is bound to an accepted request generation, so stale acceptance/send/removal cannot create or remove a newer friendship. Follow uses desired state and expected revision, independent of friend state; disabled rows remain tombstones. Notifications deduplicate by recipient/request/kind; read marking validates the entire caller-owned batch before updating. Send limits are 20 new requests per hour and 50 outstanding per sender, serialized across peers. Pair locks serialize relationship transitions, including initially absent rows. Account deletion cascades through new relationship records only.

## Post-apply execute ACL correction proposal

The original reviewed SQL SHA256 `A94BBF39041BC6C4D4A2EC6B8EDD77411EEFE9953F9134256FA536825BA05C7F` was subsequently approved and applied by Architect as `20261102144322_profile_connections_v1`. It remains immutable. Read-only post-apply inspection at 2026-11-02 14:44:04 UTC found the private mutation function still had default PUBLIC EXECUTE: the original transaction revoked temporary owner membership before its final ACL commands. PostgreSQL emitted permission warnings rather than aborting, so migration success did not establish correct ACLs. Wrapper access and the function's actor checks remained in place; that does not satisfy the intended explicit execute policy.

`profile-connections-execute-acl.sql` is a separate LOCAL corrective proposal. It reacquires only temporary function-owner membership (explicit INHERIT/SET), revokes PUBLIC/anon/authenticated execution on the private mutation function, grants authenticated execution, then removes the temporary membership. It creates no schema privilege, changes no function body/owner, and touches no application data, existing table ACL, RLS, Storage or Auth contract. The automatic creator ADMIN-only record is preserved.

`tests/profile-connections-acl.test.mjs` replays prerequisite canonical migrations plus the immutable original under a non-superuser migration owner, reproduces the observed PUBLIC ACL, applies the corrective SQL only in disposable PGlite, then verifies all six ACLs, unchanged function bodies/owners/configuration and table identities/ACLs, authenticated wrapper read, anonymous denial and removal of temporary SET/INHERIT/schema-CREATE powers. This is not a hosted application RPC or write test.

Original approval did not authorize this follow-up live correction. Require independent review, stable corrective hash and separate product-owner approval explicitly naming the execute-ACL correction and project `gwybjhqgnrpouwcdvusi` before canonical promotion or application. After any approved apply, inspect actual ACLs and migration history again; do not invoke relationship mutations as post-apply verification without separate authorization.

## Managed Auth identity bridge proposal

After separate owner approval, Architect applied the execute correction as `20261102150055_profile_connections_execute_acl`; read-only catalog inspection at 15:01:34 UTC confirmed all six intended execute ACLs. Later phone read-only activation still failed. Fresh metadata at 2026-11-02 15:08:23–15:10:05 UTC confirmed `connection_rpc` has no auth schema USAGE; installer postgres has auth USAGE and UID execute, but neither grant option. The original GRANT statements only warned. Its three PL/pgSQL actor initializers resolve `auth.uid()` at runtime, which requires auth schema lookup. The existing six RLS policies already store resolved `auth.uid` OIDs and need no replacement. The repository's earlier integrity-hardening migration documents this same managed-Auth restriction; earlier fixtures incorrectly granted installer grant options and did not reproduce it.

`profile-connections-auth-identity.sql` is a new LOCAL proposal, not yet approved for live application. Its exact-source/owner/execute precondition verifies the three known function bodies and a single UID expression before changes. It creates dedicated installer-owned `private.connection_uid()` with stable SECURITY DEFINER, empty search path and the sole body `select auth.uid()`. The helper takes no actor input, reads no user table and delegates unchanged request/JWT identity semantics to managed Auth. PUBLIC and every non-owner default execute grant are removed before granting `connection_rpc` only. A temporary explicit INHERIT/SET owner-role grant allows replacing only the three actor initializers with `private.connection_uid()` while retaining function owners, existing ACLs and other logic; it is revoked before commit. No auth object/schema ACL, existing integrity-helper ACL, RLS policy, wrapper or Storage change is proposed. `connection_rpc` remains unable to use auth directly and retains its existing narrow table privileges.

`tests/profile-connections-auth-identity.test.mjs` reconstructs managed Auth under a distinct owner, installer USAGE/execute without grant options, original source plus execute correction under a non-super installer, and the original three `42501` failures. Both INHERIT/NOINHERIT bridge installers pass local summary/list/request/accept fixtures with UUID sub and JSON claims, anonymous/null/third-party denial, unchanged six policies/Auth definitions/function owners/ACLs/configuration, default-extra-grantee stripping, and absent temporary powers.
