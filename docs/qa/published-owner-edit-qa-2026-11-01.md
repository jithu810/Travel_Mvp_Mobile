## Findings requiring assigned application fixes

1. **Medium: recovery compares only millisecond precision.** `hasSameBaseVersion` uses Date.parse, so a snapshot at `2026-11-01T10:00:00.123456Z` is accepted against loaded publication version `2026-11-01T10:00:00.123457Z`. Restore adopts the loaded version token, potentially hiding a newer published save with older local edits and then bypassing the expected optimistic conflict. New recovery regression fails. Compare exact instants at full timestamp precision while retaining existing equivalent-timezone support.
2. **Low: cancelled republish callback remains valid.** A retained callback from the Republish alert can submit after Keep editing or dismissal because it checks focus/latest/lifetime/lock but not the active prompt identity. Blur and intervening edit protections pass. Invalidate and consume an alert-specific token on confirm/cancel/dismiss; an old prompt must not consume a newer prompt. New actual-component stale-callback test fails for cancellation.
3. **Low, mode defense: local field patches can clear the published-edit flag.** Settings onChange accepts Partial<CreateForm> and spreads `{editingPublished:false}` into the form. Although existing user-facing controls emit normal field patches, clearing this invariant can re-enable draft photo checkpoints in future shared code. Pin mode to the trusted loaded editor mode on local changes/recovery. New component invariant test fails.
4. **Low, copy: Settings/progress still describe private saves.** Published-edit Settings footer says “Saves all current journey changes privately.”; photo progress says “Checking private draft...”. The save is device-only staging until explicit republish. Use mode-appropriate wording in the existing slots. No layout expansion is needed. This is source-inspection evidence, not a claim that the published draft behavior writes remotely.
5. **Medium, physical cancellation regression: slider stays stuck after dismissing the alert.** Architect reports a settled physical-device screenshot after Android Back dismissal showing “Preparing to republish” and spinner indefinitely, with no dialog and no write. Source confirms SwipeAction resets opening/busy only when its action/active/resetKey/etc. dependencies change; cancellation currently changes only a ref. Added actual-parent regression asserts resetKey changes on Keep editing and onDismiss, with zero writes; it fails. Add prompt state/reset revision so cancellation resets the existing slider. Physical evidence belongs to Architect (temporary `published-cancel.png`), not this QA specialist.

Architect received each finding immediately. Application fixes belong to Mobile specialist; QA has not changed app code or weakened failing assertions.
