### Minimum viable local design

1. Prepare Mobile-owned Supabase backend artifacts, not Web edits: a review migration, an `email-registration-status` Edge Function and isolated tests. No live creation, migration, secrets provisioning or function deployment is authorized.
2. Public Edge POST accepts only a bounded JSON body with normalized, syntactically valid email. It sends no email and creates no account/session. Return only `{ exists: boolean }`; no id, confirmation status, name, provider or metadata. Error/timeout/rate-limit responses must keep the email step visible and never assume new-account status. Use no-store responses and never log raw email/IP.
3. One narrowly scoped public-schema RPC, executable only by service_role, accepts email and limiter keys and atomically limits then performs an EXISTS query against auth.users. Revoke EXECUTE from PUBLIC, anon and authenticated in the same transaction; no grants on auth.users or limiter table to app roles. SECURITY DEFINER is justified only for this server-only bounded query; fixed empty search_path and fully qualified relations. Avoid returning Auth rows. Use auth.users existing lower(email) index only after checking its actual definition and uniqueness/provider semantics before coding; provider/SSO accounts should count as existing, even if password sign-in is unavailable.
4. Store counters in a private RLS-enabled table with no app-role access. Atomic PostgreSQL locking/upsert prevents multi-instance races; limit before checking existence. Start with independent global per-minute/per-day and per-normalized-email limits (example 30/minute, 1000/day, 3/email/15min, configurable and tested). A global counter prevents a user-controlled key from bypassing every limit, at the cost of an attacker being able to exhaust the public quota. HMAC email keys server-side with a separate server secret; no EXPO_PUBLIC secret. Expire old keys, bound storage growth, and never expose counters externally. Existing Supabase Auth rate limits do not automatically protect a custom Edge/RPC route.
5. Add a per-IP limit only when the deployed gateway's trusted client-IP header semantics have been verified. Do not trust arbitrary X-Forwarded-For or a client-supplied device id. Missing trusted-IP configuration must not bypass global/email limits. In-memory maps alone are insufficient across Edge isolates. A managed Redis limiter is supported by Supabase guidance but would introduce another integration; PostgreSQL counters reuse the current stack.
6. Mobile calls the Edge Function using its publishable client, which is a public identifier rather than proof of identity. Existing result switches to sign-in with the entered email, clears password/name as appropriate and provides guidance. New result proceeds to details. Abort or ignore stale lookups after email edits/back/mode change/unmount, lock duplicate Continue calls and keep existing final signup validation/session handling. A lookup-to-signup race remains possible; final signup still needs explicit duplicate/error/ambiguous-success handling.

### Enumeration tradeoff and rollout gate

An endpoint returning existing/new status necessarily reveals membership to callers. Throttling and CAPTCHA reduce abuse; they do not eliminate this disclosure. An email-ownership verification step before branching could avoid public enumeration but changes the requested immediate flow and introduces additional mail/verification behavior. CAPTCHA would require an owner-selected provider, configuration and native challenge UX; do not silently provision it or claim CORS/public keys prevent enumeration. Exact immediate routing therefore needs explicit acknowledgment of this product tradeoff before production rollout. It can be prepared and tested locally under the current implementation request.

## Duplicate registration semantics

[Current JavaScript signUp documentation](https://supabase.com/docs/reference/javascript/auth-signup) explicitly warns that existing-account information can be hidden. Installed auth-js GoTrueClient.ts remarks describe obfuscated success when both confirmation options are enabled, and explicit already-registered errors in other configurations. [Official Auth signup source](https://github.com/supabase/auth/blob/master/internal/api/signup.go) implements this distinction and also empties identities for invited users, so empty identities must not be treated as reliable duplicate detection.

The changelog Markdown fetch was attempted but the web tool rejected its content type. Hosted confirmation configuration and hosted Auth binary revision were not independently inspected; therefore do not assume all duplicates emit an error or promise an email was sent. This limitation does not block a configuration-independent UI change.

Recommendation: locally validate email only on Continue without any Auth/network call. Submit the existing signup request only after name/password validation. Handle the supported explicit `user_already_exists` code with sign-in guidance. For no-session success use conditional wording such as: “If this is a new email, check your inbox to confirm your account, then sign in. Already registered? Sign in with your existing password.” Preserve null-session gating; do not claim account creation, email delivery or duplicate certainty.
