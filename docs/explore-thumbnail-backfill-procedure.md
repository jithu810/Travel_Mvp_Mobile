   ```powershell
   python scripts/prepare-thumbnail-backfill.py --input <private-directory>/manifest.json --output <new-private-review-directory>
   ```

   It makes no network calls. ## Legacy naming and activation

The client derives thumbnails only from canonical `.full-v1.jpg/png/webp` references. Adding a `.thumb-512-v1.jpg` sibling to a legacy `UUID.jpg` reference alone has no effect. The existing preparer proposes a byte-identical `.full-v1.*` original copy plus the `.thumb-512-v1.jpg` sibling. Every affected reference must move deliberately to the full-v1 path after both objects are verified. This transition includes backend authorization records maintained by the approved save path; a direct blanket SQL UPDATE could break integrity and is prohibited.

The existing preparer is **not** a live executor. The subsequently authorized bounded helpers are `scripts/explore-cover-backfill-plan.mjs` and `scripts/explore-cover-backfill-upload.mjs`; their reviewed design uses one canary followed by the remaining eight. The upload helper cannot activate database references; separate exact-manifest SQL is reviewed/executed through the confirmed maintenance connection only after object hash/version verification. Their contract includes:

- Explicit approved target, exact manifest hashes, maximum item/byte budget, and a single selected canary before any wider batch.
- Fresh source version/hash, ownership/provenance, current reference, and `updated_at` checks immediately before action. Fail closed on drift or unknown identity. Shared references must be enumerated, not silently rewritten.
- Create-only Storage uploads (`upsert:false`), no overwrites. If a destination exists, compare its bytes/hash to the manifest and record verified-existing only when identical; conflict or uncertain upload outcome stops that item. Reconcile remote state before retrying; never blindly upload again.
- Verify original-copy SHA256 and thumbnail SHA256, JPEG format, positive dimensions with longest side <=512, size <=1 MiB, and expected content type. Record receipt/object version. Use bounded concurrency, batch size and timeouts.
- Only after both objects verify, use an approved owner-authorized optimistic save/reference transition preserving all other journey fields and stop ordering. It must compare the prior path and concurrency token, update the legitimate media authorization state, and not accidentally publish drafts. Existing save RPC behavior and shared references require a separate integration design; the procedure does not authorize bypassing it with privileged SQL.
- Check anonymous access to a published canary thumbnail, owner access to a private canary, and denial for another user's private source/thumbnail in an isolated environment first. After separately approved live canary activation, check authorized reads only; never create production test users/records implicitly.
- Per-item durable receipt states: planned, source-verified, original-created/verified-existing, thumbnail-created/verified-existing, pair-verified, reference-transitioned, access-verified, or stopped. Include old/new references, object versions/hashes and before/after concurrency tokens. Resume only from reconciled receipts under the same approved scope; do not reuse expired approval for changed manifests.

## Recovery and rollout

Do not delete any original or newly uploaded pair automatically. If verification fails before reference transition, leave the old reference active and stop; unreferenced uploaded pairs are harmless pending review. If activation fails, stop the batch. Separately approved rollback may restore the old reference only if current reference and version still match the activation receipt, through the reviewed authorized save path. It must not overwrite later user edits. Storage cleanup/deletions and policy rollback require separate explicit approvals and their own manifests. Retain receipts until recovery is verified.
